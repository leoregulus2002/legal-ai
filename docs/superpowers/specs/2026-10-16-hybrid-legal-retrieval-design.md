# 内部法律知识库混合召回设计

日期：2026-10-16

状态：用户已要求直接开发，跳过后续计划确认。功能说明和检查边界见 `docs/legal-consultation.md`。

后续范围调整：用户要求补齐“添加内部知识库”，现咨询仅检索策略所选内部库，外部 HTTP 路径已移除。下文外部路径保留条款记录最初混合召回任务的范围，当前行为以使用文档为准。

## 目标与范围

用户选择使用混合召回，并随后明确要求暂不使用相关性重排序模型。
本次目标是让内部知识库同时利用法律术语的词项匹配和自然语言问题的向量匹配，
再通过 RRF 合并结果，减少当前只能二选一检索造成的遗漏。

范围包括内部知识库搜索和法律咨询调用内部知识库的路径；继续使用现有
PostgreSQL、pgvector、jieba、SQLAlchemy、FastAPI 和 Vue 技术栈。
内部知识库搜索默认使用混合召回；现有显式 `model_id` 参数仍可指定向量路的模型，
指定时只查询该模型指纹匹配的索引，不改用其他模型。

本次不接入 Reranker，不添加 MMR，不增加模型供应商、AI 框架或独立搜索服务。
此前已停止的“外部接口改为添加内部知识库”需求不在本次范围内；
现有外部检索路径继续按其原有协议处理，混合召回仅作用于内部知识库。

## 当前实现

- `KnowledgeService.retrieve_local` 找到第一个配置指纹匹配、已启用的向量模型后，
  立即返回该模型空间的向量结果；此时不会同时检索关键词。
- 没有可用向量模型时，对问题提取关键词，按片段包含的关键词占比评分。
  这不是 BM25。
- 仓储层仅搜索未删除知识库中已发布文档的当前版本正式片段。
- 法律咨询默认取 5 条，并在取回后按默认 0.7 的相关度阈值过滤。
- 不同模型的向量空间已有配置指纹和维度隔离，不应混用。

## 选定流程

```text
文字问题与知识库范围
  ├─ 中文词项处理 → BM25 候选
  └─ 匹配索引的 Embedding 模型 → 余弦候选
             ↓
       按正式片段 ID 去重
             ↓
       RRF 合并两路排名
             ↓
       按请求数量返回结果
```

两路候选在同一知识库、发布状态、文档版本范围内生成，每路默认最多 50 条。
这里的“同时召回”指两路都参与选择；不得在同一个 AsyncSession 上并发执行 SQL。
模型网络调用与 SQL 查询按现有请求 Session 的约束顺序组织。

RRF 公式为 `sum(1 / (60 + rank))`，排名从 1 开始，两路使用相同权重。
同分按片段 ID 排序，确保翻页与重试时具有稳定顺序。
相同片段在两路都命中时累加分数，而不是重复出现在结果中。
本次只合并相同片段 ID，不按文本相似度删除主规则、例外或相邻条款。

## BM25 索引与评分

在正式片段 `knowledge_chunks` 增加：

- `lexical_terms`：JSONB 词项频次字典。
- `lexical_length`：实际参与索引的词项总数。
- `lexical_version`：分词规则版本，用于识别尚未建立或需要更新的索引。
- `lexical_terms` 的 GIN 索引，用于筛选包含查询词项的候选片段。

使用 jieba 对正文分词并统一大小写、过滤空白和标点。
索引保留法律术语、数字和否定词，不沿用仅保留名词的提词策略，
避免丢掉“不”“未”等可能影响适用条件的信息。
查询与文档必须使用相同的词项规范化规则；查询词去重并设置数量上限。
查询阶段额外过滤问句泛词和语气词，索引仍保存正文词频，不移除否定条件。

采用标准 BM25 评分：

```text
IDF(term) = log(1 + (N - df(term) + 0.5) / (df(term) + 0.5))
score = sum(IDF(term) × tf × (k1 + 1)
            / (tf + k1 × (1 - b + b × length / avg_length)))
k1 = 1.2，b = 0.75
```

语料统计基于当前检索范围内、已发布的有效片段。
仓储层通过 SQL 计算统计值和候选评分，不把全部正文加载到应用内存后逐篇扫描。
BM25 原始分数不当作 0–1 概率，不直接与余弦分数相加。

## 发布与历史资料

新增 Alembic 迁移，创建上述索引字段和 GIN 索引。
迁移不调用模型，不修改原件、法律文本和审核结论。

新资料审核发布时，在工作线程完成分词，在发布事务中保存词频索引和正式片段，
使新发布片段立即具备 BM25 检索能力。撤回、删除与重新发布仍沿用正式索引的生命周期。

已有已发布片段由后台维护任务分批补建词频索引；每批使用独立事务，
写入时检查片段和文档版本，支持重复执行和中途恢复。
查询范围内存在尚未补建的正式片段时，明确提示索引正在准备，
避免将仅搜索部分资料的结果当作完整检索结果。

## 向量选择与异常处理

保留当前按发布时间寻找可用 Embedding 配置的规则，
一次检索只使用一个指纹、维度均匹配的向量空间。
BM25 候选可以包含尚未向量化的已发布片段。

有可用向量索引时，BM25 与余弦两路都执行；某一路没有候选不阻止另一路返回。
没有可用向量模型或匹配索引时，保留 BM25 单路检索，响应携带实际检索方式，
界面说明本次为关键词检索，不能声称执行了混合召回。
已选中的向量服务超时、认证失败或返回异常时，按真实异常提示用户，
不将服务失败解释为知识库没有对应资料。

两路均无候选时，内部搜索返回空列表；法律咨询沿用“知识库找不到对应信息”的回答。
法律咨询知识库关闭时不执行上述检索。

## 分数、阈值与界面

RRF 分数与现有余弦分数不是同一种尺度。
内部混合召回不能继续拿融合分数套用原来的 `0.7` 阈值。

响应保留可追溯的 BM25 分数、余弦分数和两路排名，新增融合分数及实际检索方式。
保留现有来源所需的 `score` 字段：向量命中时使用余弦分数，
只有 BM25 命中时使用查询词项覆盖率，并明确标识分数类型。
该字段仅用于兼容展示，不决定融合后的排序，也不表示法律适用概率。

法律咨询对内部检索不再用旧相关度阈值过滤融合结果，
改用可选的“最低向量相似度”和“最低关键词覆盖率”作为各路候选的独立门槛，
初始值分别为 0.3 和 0，以保留真实匹配候选。
配置字段为 `knowledge_vector_threshold` 和 `knowledge_keyword_threshold`，
均存于现有咨询策略 JSON，旧配置缺失时使用上述默认值。
最终数量继续由现有“最多引用资料数”控制，默认 5 条。
外部知识库继续使用其原有相关度阈值，避免改变外部接口的分数约定。

知识库搜索页展示实际检索方式，避免将 RRF、BM25 或余弦分数混为同一种“相关度”。
请求和业务异常统一通过现有 Naive UI 弹出提示处理，不将错误渲染在正文中。

内部混合候选集合最多 100 条，按融合后的集合稳定分页；
返回的 `total` 表示本次候选集合的数量，界面注明为候选结果，
不得解释为全库所有相关片段的精确数量。

## 模块职责与文件

- `app/modules/knowledge/retrieval.py`：中文词项处理与 RRF 合并等纯逻辑。
- `app/modules/knowledge/models.py`、迁移：词频索引存储结构。
- `app/modules/knowledge/repository.py`：范围过滤、BM25 统计及评分、余弦候选查询。
- `app/modules/knowledge/service.py`：选择向量模型、组织两路召回与返回结果。
- `app/modules/knowledge/worker.py`：旧片段索引的批量维护。
- `app/modules/knowledge/schemas.py` 与前端类型：分数来源、实际检索方式。
- 法律咨询 Service 与配置：内部候选门槛、引用数量及来源快照。
- 知识库搜索页、使用文档：展示和说明新的检索行为。

Router 不直接查询数据库；Repository 不承担分词、融合或降级的业务决策。
不新增通用检索框架、抽象基类或独立微服务。
